# Architecture

Lighten is a Swift Package Manager project for macOS 26 and later. It has no Xcode project and has six targets:

- `Lighten` is the executable target and owns the SwiftUI application entry point. It declares no SwiftPM resources.
- `LightenKit` is the library target. It contains reusable application logic and a bundled Clean catalog that can be exercised independently by `LightenKitTests`.
- `CLightenPlatform` is a small C layer over Darwin APIs. It parses `getattrlistbulk` directory metadata for the scanner; reads memory pressure, swap and per-process resource usage; observes which current-user processes run from or hold files under a path, without reading process arguments or environment; and sends SIGTERM or SIGKILL only to a process record it has just revalidated.
- `LightenBench` is a command-line measurement tool (`lighten-bench`) for scan engines. It creates and reads only its own synthetic trees and otherwise observes metadata.
- `LightenKitTests` verifies the library and repository resource contracts.
- `LightenAppTests` verifies application state and confirmation flow.

The executable depends on `LightenKit` and `CLightenPlatform`. `LightenKit` depends only on `CLightenPlatform` and has no external package dependencies.

The repository-level `Resources/` directory contains application-bundle inputs. `scripts/package_app.sh` copies the property list, privacy manifest, and SwiftPM resource bundle, compiles `Localizable.xcstrings` into language-specific strings files and the Icon Composer document `Resources/AppIcon.icon` into the Liquid Glass app icon, and assembles them in the application bundle. SwiftUI localization resolves those compiled strings through `Bundle.main` at runtime. A packaged app loads its Clean manifest only from `Contents/Resources/Lighten_LightenKit.bundle`; missing resources fail closed.

## Contracts

### NeverRule

`NeverRule` defines a protected cleanup pattern with a stable identifier, a user-facing reason, and optional supporting evidence. `NeverRule.all` is the canonical ordered collection of locations and operations that Lighten must never offer for cleanup. Consumers must preserve these protections before presenting cleanup choices. `PathPattern` matches absolute path components: `*` matches characters within one component; `**` matches zero or more complete components. Consequently, `X/**` includes `X` itself. A leading `~` expands to an injected home directory so tests and future scanners use the same rule set without depending on the host user's home.

### Bundle identity and version

`LightenIdentity.bundleIdentifier` is the Swift identity source. The source `Info.plist` identifier must match it; tests and `scripts/package_app.sh` enforce that equality before signing. The package script signs with the value from the validated plist and checks the signed result. `LightenVersion` owns marketing and build versions; the source plist keeps placeholders that the package script replaces.

### SafetyDocument

`SafetyDocument.markdown(rules:)` renders a set of `NeverRule` values as the checked-in safety reference at `docs/SAFETY.md`. Its default input is `NeverRule.all`; `SafetyDocumentTests` verifies that the generated output and checked-in document stay identical.

### Scan and action values

`ScanEngine` measures an explicit directory root with a bounded pool of worker threads. Each worker opens one directory without following links, reads its entries with bulk metadata calls, closes it, and only then queues child folders, so open directory descriptors never exceed the worker count. The first level is read before deeper work; work beneath the folder on screen can be prioritized. Results go into a lock-protected `ScanTree` whose nodes are folders and packages; each folder keeps its largest files and one summary of the rest. Totals propagate upward as folders are read, and a folder is complete only when all of its descendants are. Until then its value is a known lower bound. Hard-linked files count once per scan. Symlinks are leaves and are never followed. Other volumes are not entered. Packages are one node whose total includes their contents. NeverRule areas are summed from metadata only and expose no children or actions; `~/.ssh` and `~/Library/Keychains` are never opened; cloud-backed areas and dataless folders are not enumerated. A scan of `/` walks the Data volume once under its firmlinked names and shows the sealed system volume as a single measured block. A throttled progress stream publishes at most eight times a second; reading the tree is proportional to the children of one folder. The last finished tree per root is cached for an instant first screen and is always labeled with its scan time.

A scan tree supplies display observations, never mutation authority. An explicit user selection captures only the current root identity, collapses nested selections and binds the exact plan privately to its removal method. Confirmation does not walk descendants or require application metadata, complete scan totals, recommendation proof or descendant protection exemptions. Known valuable content produces a nonblocking warning with one example path. Symbolic-link roots move as links. Base directories and Lighten itself remain protected, including physical aliases. Lighten does not move items owned by another user: it shows the administrator-permission reason and offers Show in Finder, where the user can perform the move with Finder's authorization flow. Legacy strict plans remain readable and cannot acquire user-selection authority from a serialized marker.

Clean catalog, application data and duplicate discovery use `ScanEngine`. Their cached results contain presentation fields only and cannot authorize a plan. `ScanService` remains the snapshot scanner for fresh, bounded action evidence such as selected catalog items and duplicate files. It traverses descriptor-relatively and stops at protected locations, symlinks, volume boundaries, dataless items, and packages; unknown or unreadable entries make ancestor totals partial. `ScanService.scanImmediateChild` observes one named child and its complete safe subtree beneath a real parent without traversing siblings. `PlanService.makePlan` turns snapshot entry IDs into strict plan items.

Space shows the live tree as a descending folder list and a deterministic area-proportional rectangle treemap. Disk used/free comes from a separate volume measurement, not the scan total. Selected Space items, whole apps, and Clean Trash candidates use the same action presentation, confirmation, executor, and history. Motion applies to state transitions and respects Reduce Motion.

### Execution, journal, and undo

`ActionExecutor` executes explicit confirmation plans through their private root binding before any legacy inventory or installed-owner preparation. It checks root identity and base protections again after the final hook, observes running executables under each selected root, and closes only native PID/start/executable-vnode-proven applications and helpers when the user chose close and remove. Graceful application quit precedes any confirmed force step. Confirmation plans do not repeat discovery ownership, signing, metadata, descendant protection, duplicate hashing or subtree inventories. Legacy strict and catalog callers retain their existing proof validation until an explicit selection adapter replaces that authority. The executor serializes each plan under an exclusive nonblocking journal lease, refuses plan reuse, and durably stores its plan file and SHA-256 reference before mutation. Legacy inline records remain readable. Journal directories, lock and journal files are owned by the current user and synced; invalid event sequences remain visible and block mutation. History summaries avoid loading every plan inventory. An optional user-selection recovery marker is provenance only and cannot recreate a private execution binding.

The bundled versioned catalog declares exact home-relative category roots, permitted recommendation methods, minimum age and automatic-selection policy. Discovery continues to reject traversal, unsupported roots and protected recommendation content. Catalog proofs do not authorize arbitrary configured paths. Clean activity observations remain scoped to relevant tool roots; shell names alone do not veto unrelated caches. A user explicitly selecting a discovered row replaces catalog authority with the same root-only confirmation plan used elsewhere. Permanent removal requires a plan-bound irreversible confirmation and deletes through pinned parent descriptors with no-follow unlinkat. Traversal happens during removal, not as a preconfirmation inventory; actual deleted counts and known bytes are journaled, and partial failures remain visible. Legacy catalog deletion keeps its strict checks.

Application data discovery covers standard user Library locations and native framework/configuration evidence. Exact bundle identifiers, signed ownership, authenticated package artifacts, settings and complete native live observations establish suggested relationships. Name-only, sole live-process and sole vendor-directory candidates remain unselected. A vendor directory needs exclusive signing-team and bundle-prefix evidence; common framework/tool caches are excluded, and automatic selection requires an independent durable proof. Live evidence cannot claim Documents, Desktop, Downloads, another home or cloud storage. Shared physical owners are named and never suggested. Group-container ownership requires complete owner/signature evidence. Incomplete global registration blocks group and nonexact claims while relevant exact-identifier relationships remain available. The app and user-selected data share one root-only confirmation, journal plan and grouped Undo. Related data found after the app has been removed is shown unselected and requires its own confirmation and Undo group. Discovery evidence is collected once per snapshot and remains recommendation evidence, not a reason to refuse a subsequent explicit user choice. Identifierless applications can still be selected without inventing an identifier. CoreSimulator device packages remain separate observations with their own reason and next step. Cached, build, simulator, Trash and dependency copies do not become installed owners merely by their names.

Application ownership discovery may invoke only read-only system tools: `/usr/sbin/pkgutil` with `--pkgs`, `--files <identifier>`, or `--pkg-info-plist <identifier>`; `/usr/bin/mdutil -s /`; and the absolute LaunchServices support executable with `-dump` when Spotlight is disabled or unavailable. These bounded queries run off the main thread at most once per scan, with a fixed locale and no shell. Spotlight and registry output provide discovery leads only; native no-follow metadata and signing observations verify every candidate. Incomplete global discovery leaves shared-container and literal ownership unavailable without disabling otherwise complete exact-identifier relationships.

The application Trash adapter calls Foundation off the main actor and records its actual returned path and native moved-root identity. An unverified result or failed applied append is uncertain. Explicit selections recover from this returned path and root identity without descendant inventories, application metadata or missing legacy Undo-proof requirements. Changed or missing returned items remain visible, and Undo never replaces an occupied original name. It appends durable undo intent, pins the current destination parent, checks the same parent after the journal await and uses an exclusive no-follow rename. An append failure after rename leaves a reconcilable intent. Legacy strict records retain their established identity checks. History never enumerates or empties the system Trash; grouped Undo continues across collisions and independent failures. Permanent history shows irreversible or partial results and provides no Undo. Size and warning observations remain display-only.

Foundation Trash accepts a path, so validation and the move are not an atomic identity-bound operation; a concurrent change in that final window remains a documented limit. Root identities may become unusable after a reboot or remount, in which case recovery stays uncertain rather than guessing. Trash bytes are pending, not reclaimed disk space. Only Lighten actions appear in its history. A damaged journal can be explicitly archived and restarted while preserving valid pending Trash records. An owned regular journal with loose permissions is repaired to mode 0600.
