# Architecture

Lighten is a Swift Package Manager project for macOS 26 and later. It has no Xcode project and has six targets:

- `Lighten` is the executable target and owns the SwiftUI application entry point. It declares no SwiftPM resources.
- `LightenKit` is the library target. It contains reusable application logic and a bundled Clean catalog that can be exercised independently by `LightenKitTests`.
- `CLightenPlatform` provides a narrow current-user process metadata check without reading process arguments or environment, and parses `getattrlistbulk` directory metadata for the scanner.
- `LightenBench` is a command-line measurement tool (`lighten-bench`) for scan engines. It creates and reads only its own synthetic trees and otherwise observes metadata.
- `LightenKitTests` verifies the library and repository resource contracts.
- `LightenAppTests` verifies application state and confirmation flow.

The executable depends on `LightenKit` and `CLightenPlatform`. `LightenKit` depends only on `CLightenPlatform` and has no external package dependencies.

The repository-level `Resources/` directory contains application-bundle inputs. `scripts/package_app.sh` copies the property list, privacy manifest, and SwiftPM resource bundle, compiles `Localizable.xcstrings` into language-specific strings files, and assembles them in the application bundle. SwiftUI localization resolves those compiled strings through `Bundle.main` at runtime. A packaged app loads its Clean manifest only from `Contents/Resources/Lighten_LightenKit.bundle`; missing resources fail closed.

## Contracts

### NeverRule

`NeverRule` defines a protected cleanup pattern with a stable identifier, a user-facing reason, and optional supporting evidence. `NeverRule.all` is the canonical ordered collection of locations and operations that Lighten must never offer for cleanup. Consumers must preserve these protections before presenting cleanup choices. `PathPattern` matches absolute path components: `*` matches characters within one component; `**` matches zero or more complete components. Consequently, `X/**` includes `X` itself. A leading `~` expands to an injected home directory so tests and future scanners use the same rule set without depending on the host user's home.

### Bundle identity and version

`LightenIdentity.bundleIdentifier` is the Swift identity source. The source `Info.plist` identifier must match it; tests and `scripts/package_app.sh` enforce that equality before signing. The package script signs with the value from the validated plist and checks the signed result. `LightenVersion` owns marketing and build versions; the source plist keeps placeholders that the package script replaces.

### SafetyDocument

`SafetyDocument.markdown(rules:)` renders a set of `NeverRule` values as the checked-in safety reference at `docs/SAFETY.md`. Its default input is `NeverRule.all`; `SafetyDocumentTests` verifies that the generated output and checked-in document stay identical.

### Scan and action values

`ScanEngine` measures an explicit directory root with a bounded pool of worker threads. Each worker opens one directory without following links, reads its entries with bulk metadata calls, closes it, and only then queues child folders, so open directory descriptors never exceed the worker count. The first level is read before deeper work; work beneath the folder on screen can be prioritized. Results go into a lock-protected `ScanTree` whose nodes are folders and packages; each folder keeps its largest files and one summary of the rest. Totals propagate upward as folders are read, and a folder is complete only when all of its descendants are. Until then its value is a known lower bound. Hard-linked files count once per scan. Symlinks are leaves and are never followed. Other volumes are not entered. Packages are one node whose total includes their contents. NeverRule areas are summed from metadata only and expose no children or actions; `~/.ssh` and `~/Library/Keychains` are never opened; cloud-backed areas and dataless folders are not enumerated. A scan of `/` walks the Data volume once under its firmlinked names and shows the sealed system volume as a single measured block. A throttled progress stream publishes at most eight times a second; reading the tree is proportional to the children of one folder. The last finished tree per root is cached for an instant first screen and is always labeled with its scan time.

A scan tree is a picture, never a grant. Space planning takes selected paths with their observed device and inode and obtains fresh, descriptor-relative, no-follow exact inventories. Nested selections collapse to one root; individual refusals retain their paths and reasons while the remaining items can share one plan. Space Trash moves symlinks and socket or FIFO descendants as leaves. Trash policies treat intact packages, including nested applications, as opaque leaves bound to freshly observed device, inode, birth time, volume, type and flags. Descendant payload metadata and an absent optional bundle identifier do not determine stable-root recovery proof; native executable-path checks still cover helpers and nested code, and freshly observed application identifiers retain self and running-application refusals. Package contents move intact. An application interior cannot be selected separately. Every nested application's identity is checked for activity before planning and execution. Device nodes, special roots, unreadable items, other volumes, cloud placeholders and unrelated protected data remain refused. Protection rules distinguish permanently protected data from items that can be explicitly selected in Space for warned, reversible Trash only. A MobileSync selection must be one whole direct backup child; backup parents and interiors remain protected. Generic cleanup and recommendation callers continue to reject both protection scopes, and permanent operations retain strict rules. Lighten never plans to remove itself. Legacy plan items without these policies decode as strict.

`ScanService` remains the snapshot scanner for bounded evidence such as Clean candidates and duplicate groups. It traverses descriptor-relatively and stops at protected locations, symlinks, volume boundaries, dataless items, and packages; unknown or unreadable entries make ancestor totals partial. `ScanService.scanImmediateChild` observes one named child and its complete safe subtree beneath a real parent without traversing siblings. `PlanService.makePlan` turns snapshot entry IDs into strict plan items.

Space shows the live tree as a descending folder list and a deterministic area-proportional rectangle treemap. Disk used/free comes from a separate volume measurement, not the scan total. Selected Space items, whole apps, and Clean Trash candidates use the same action presentation, confirmation, executor, and history. Motion applies to state transitions and respects Reduce Motion.

### Execution, journal, and undo

`ActionExecutor` prepares complete installed-owner validation before acquiring the journal lease. Signing and entitlement observations are cached only while executable and signed-metadata filesystem identities remain unchanged. During the lease, same-execution validation rechecks the selected owners' captured identities and the full Guard without a signing tour; these temporary results are never encoded or recovered as authority. The executor serializes a plan under the journal's exclusive mutation lease. The lease uses a nonblocking filesystem lock across journal instances and processes. An existing plan ID cannot be executed again; a fresh user action requires a fresh plan. The executor durably stores the complete plan inventory in an owner-only `plans/<id>.json` file before appending a compact intent containing its SHA-256 reference and item summaries. Both the inventory and intent are flushed and synced before any mutation. Legacy inline plans remain readable. Appends validate the journal incrementally under its lease; History reads summaries without loading every inventory. Newly created journal directories and their parents are synced, and journal and lock files must be regular files owned by the current user. Invalid journal event sequences remain visible as issues and block further mutation. `ActionGuard` rechecks the selected root, its ancestors, and every inventoried descendant immediately before each move, including after an injectable final hook. Opaque Trash packages are revalidated at their stable roots. A separate no-follow directory and code-boundary observation preserves protected-content, activity and mounted-image checks without treating payload metadata as recovery authority. Selected related-data ownership and metadata bindings remain independently fresh. Strict items require full metadata equality. Before a Space tree intent is recorded, the executor binds the original stable root identity and recollects its current inventory, checking process activity, nested applications and disk-image attachment. The durable plan describes that refreshed tree and the result reports changes since confirmation. After intent, the final Guard requires full equality with the refreshed inventory outside opaque package contents. Opaque package roots retain their stable Trash identity binding. Later changes elsewhere in the selected tree skip that item. Directory ancestors compare stable volume, inode, kind, and flags because moving a sibling can legitimately change their timestamps and size. A changed or newly protected child, unreadable item, mount, dataless item, or prohibited special file skips the selected root; strict items also skip symlinks and package boundaries, while tree-policy items compare a symlink's own identity and never its target. Space tree policies apply only to plain Trash items without other proofs, and the whole-bundle policy only when the root is itself an application. A bundled catalog Trash proof can authorize moving packages and symbolic links as leaves. Only the DerivedData build-output category additionally permits debug-symbol descendants; its application-slice and localization descendants move with their containing build output. Other protection rules, volume checks, identities, running-application checks and no-follow ancestry remain unchanged. Moving a whole candidate or package to the Trash is not binary thinning or localization removal: catalog Trash may carry those descendants intact, while debug symbols remain limited to build output and every permanent operation retains strict protection. Permanent plans cannot use any tree policy.

The bundled versioned catalog declares exact home-relative category roots, permitted methods, default selection and minimum age. Validation rejects traversal, protected roots and permanent authority for user data or build output. General application caches exclude Apple domains and roots owned by another category; simulator device data is report-only. The catalog never grants access to its root or an arbitrary configured path. Each plan item carries its own observation run and method-bound catalog proof, so one plan can contain several categories without sharing observation authority. Clean checks current-user open-file or working-directory evidence beneath the relevant tool category; general application caches are checked per child, including their running application. Shell or interpreter names alone do not veto unrelated caches. Activity is checked again at the final guard. Permanent plans additionally require a plan-bound irreversible confirmation. The executor independently checks the bundled manifest, per-item proof, full inventory, volume, and protection rules. It deletes each verified leaf through a pinned parent descriptor with no-follow `unlinkat`, then journals the actual irreversible count and known logical bytes. A changed remaining child or ancestor stops the action as partial. An unknown activity state blocks both Clean methods. Related items use Trash or remain report-only.

Application data is matched through one table of Caches, Preferences, Application Support, Containers, Group Containers, Saved Application State, Logs, HTTPStorages, and WebKit under the user Library. Strong matches use exact bundle identifiers; medium matches also require the signing team, and name-only matches remain unselected. A group container is never selected by default and requires every potential owner to have validated signing metadata. Ownership includes user and system application locations, nested helpers, extensions and login items. Only one containing package may claim the group, and Apple group identifiers always remain report-only. An unreadable signature or incomplete ownership inventory keeps the group report-only. Whole-container Trash plans may include Documents and symbolic-link leaves only under matching related-data proof; every other protection, identity, ancestry and volume check remains in force. Discovery uses scan-engine measurements, which never authorize actions: selected roots receive fresh exact inventories. A combined uninstall validates the package and data, then moves the package first even when selected data appeared first. Any package refusal prevents its data from moving. Only a verified applied move creates a temporary context for that same plan; data validation binds the mapped package and metadata identities at its recorded Trash location, checks that the source remains absent, and runs the full Guard. Related-data-only actions still require a fresh movable owner package at each final check. A native executable-location observation covers main apps, helpers, extensions and login items across all observed users; an unobservable live process refuses the action. The application and explicitly selected data share one confirmation, journal plan, and grouped Undo. Application discovery covers `/Applications` and `~/Applications`, and a dropped application is identified independently at its current path. Symbolic links identify apps read-only and never grant an action on their target. Unreadable or incomplete inventory cannot prove absence. An unrecorded orphan requires complete current application inventory, LaunchServices absence, a non-Apple identifier and current-user ownership, and remains warned and unselected. Metadata receipts remain bounded and owner-only; they do not authorize an action alone. Every selected item requires fresh scope and owner validation, running-app checks, Guard, and explicit Trash confirmation. Permanent operations keep strict rules.

The application Trash adapter calls Foundation off the main actor. The journal records the actual returned Trash path and its moved identity; a failed applied append or an unobservable moved result is uncertain, not a successful or failed move. Directory Trash recovery compares stable device, inode, type, volume, birth time and flags, so Finder-created directory metadata does not prevent Undo. Files retain modification-time, size and link-count checks as well, and duplicate-file SHA verification remains unchanged. Recovery allows ctime to change after a move. Older records without that proof remain uncertain. Each plan item has a result, including `notAttempted` for untouched items after an early stop. `ActionHistory` takes the same lease when reconciling or undoing, so it cannot present an in-flight state as final. It rebuilds state from durable records after restart and leaves an intent unresolved when the source is gone and the returned Trash path was never recorded. It never enumerates or empties the system Trash. Undo first appends a durable undo intent, checks the returned item and original parent, and re-resolves the parent path after the journal await. It then uses an exclusive no-follow rename into the original name. A collision preserves both items. An append failure after the rename leaves an observable undo intent for reconciliation. Permanent catalog history shows irreversible or partial outcomes and has no undo.

Foundation Trash accepts a path, so validation and the move are not an atomic identity-bound operation. A concurrent change in that final window remains a limit of this implementation; it must not be described as race-proof. The volume UUID and device number are rechecked before a move. Journaled device/inode identity may become unusable after a reboot or remount; reconciliation then remains uncertain and undo fails closed rather than guessing. Trash bytes are pending, not reclaimed disk space. Only items moved by Lighten appear in its action history. History groups every plan into one row, and one Undo restores its remaining verified Trash items while preserving collisions and partial failures. A damaged journal can be explicitly archived and restarted; valid pending Trash records survive without inventing applied events. A regular journal owned by the current user with loose permissions is repaired to mode 0600.
